Problem statement

Mature systems fail through slow entropy

Most architectural and performance regressions come from reasonable local changes that add up over time.

What AI-SDLC does differently

  • Just-in-time guidance - AI flags the risk and shows the fix in the workflow.
  • Repo-wide context - check diffs against patterns, conventions, and past failures.
  • No fatigue - consistent rule application across thousands of changes.
  • Humans still own judgment - trade-offs, intent, and "good enough".

What it is not

The lifecycle

Three phases, explicit gates

AI-SDLC is adaptive, but it never skips: requirements clarity, plan approval, and validation evidence.

Interactive

Lifecycle map

Phase A: Inception
Phase B: Construction
Phase C: Operations

Goal: convert intent into testable, decomposed work.

  • Intent + success metrics
  • Requirements + constraints
  • NFRs (security, performance, availability)
  • Units of work + acceptance criteria
  • Level-1 execution plan
Gate: Inception approved

Goal: build each unit with proof, in small diffs.

  • Per-unit plan and (right-sized) design
  • Implement small diffs
  • Verification: tests, lint, build, scans
  • Validation report: what ran and results
Gate: Unit done (evidence + review)

Goal: deployable, observable, rollbackable.

  • Deployment plan + rollout strategy
  • Runbooks + observability (dashboards/alerts)
  • Cost review and controls
  • Security evidence
Gate: Production readiness

Four lenses (so it works across roles)

  • Engineering - stabilize a high-gain actuator with tight feedback loops.
  • DevSecOps - treat outputs as untrusted until proven by checks and runtime evidence.
  • Product - intent clarity is context compression; vagueness causes rework at machine speed.
  • Change leadership - adoption is a cultural refactor: new rituals, roles, and practice.

Anti-pattern to avoid

"Big low-confidence code dump" + humans forced to review and own a diff they do not understand.

Safety and scalability

The non-negotiables

These rules make AI use safe, reviewable, and repeatable at BU scale.

Presenter tip

Keep returning to three anchors: plan-first, small batches, proof over prose.

Rules (progressively reveal)

  • Human accountability - humans own decisions and outcomes.
  • Plan-first, stage-by-stage - stop for approval before executing meaningful work.
  • Small batches (units) - keep diffs reviewable and reversible.
  • Persisted artifacts - store requirements, plans, evidence in the repo.
  • Proof over prose - "done" means tests/checks + validation report.
  • Tooling for truth - prefer authoritative retrieval and runtime inspection.
  • Safety constraints explicit - define data/tool boundaries; stop on risk.
  • Separation of concerns - bounded roles/agents; avoid one agent doing everything.

Execution

Per-unit loop: plan - build - prove

AI accelerates execution. Rails prevent the bottleneck moving to review, CI, and production risk.

Presenter prompt

Ask: "What would you need to see to merge an AI-generated PR with confidence?"

The loop (one unit)

  • AI drafts unit plan (checkbox tasks, risks, test strategy)
  • Human approves plan (or refines scope)
  • AI drafts design (APIs/data model/trade-offs)
  • AI implements in small diffs
  • AI runs verification (tests, lint, build, scans)
  • AI writes validation report; human approves merge

Rails (defaults)

Small PR discipline

Prefer one unit per PR. Avoid mixing refactors and features.

Multi-stage review gates

Static checks, security checks, integration/contract checks, complexity checks, then human approval.

Receiver infrastructure

Stronger tests, CI/CD, feature flags, and observability so higher velocity does not reduce quality.

Second-order effect

If you do not raise verification, you will ship faster and fail faster. AI-SDLC is designed to prevent that.

Variants

Brownfield: discovery is mandatory

For existing systems, no coding until discovery is complete and approved. For frontend, runtime proof is mandatory.

Presenter tip

Call out: most BU value is in brownfield, so this is where AI-SDLC either earns trust or fails.

Discovery and analysis (before inception)

  • Analysis plan - what we will inspect and how.
  • Current-state analysis - architecture, dependencies, integrations, infra constraints.
  • Regression baseline - "must not break" behaviors.
  • Change impact - what modules, data, and contracts are touched.
  • Semantic models (backend) - static + dynamic models for key flows.
Gate: Discovery exit approved

Frontend constraint: preserve working behavior

  • "Do no harm" - changes in behavior require explicit approval.
  • Runtime validation - real browser checks (and/or E2E) are mandatory.
  • Evidence capture - DevTools/network/perf proof where relevant.

Why this matters

Brownfield mistakes are expensive. Discovery + baselines create the guardrails AI needs to be helpful instead of disruptive.

Adoption

Gym - scale - BAU

Adoption is a cultural refactor. We start with practice on real work, then template it, then make it routine.

Audience callout

Non-technical colleagues are critical: intent, constraints, acceptance criteria, and gatekeeping.

30/60/90 (suggested)

0-30 days: pick a slice

  • Choose sponsor + technical owner.
  • Select one bounded backlog item (1-3 units).
  • Baseline lead time, defects, rework, review backlog.

30-60 days: run the Gym

  • Mob elaboration (intent - units - plan).
  • Mob construction (one unit end-to-end with proof).
  • Capture templates + guardrail backlog items.

60-90 days: make it routine

  • Standardize aisdlc-docs and approval gates.
  • Integrate review gates into CI/CD where possible.
  • Publish a "lighthouse" win and what you learned.

Roles (minimal set)

  • Sponsor - outcome target, trade-offs, unblock.
  • Pod lead - unit boundaries, acceptance criteria, execution plan.
  • Engineer(s) - operate agents, keep diffs small, keep artifacts coherent.
  • QA / Ops / Security - engage by risk, own verification and readiness evidence.
  • AI workflow maintainer - prompts, rails, CI gates as code.

Rituals (recommended)

Mob elaboration (30-60m), bolt planning (15m), mob construction (60-120m), guardrail retro (15m).
